# HomeAsset Companion 开发计划

> 基线：v1.3.0 账单与提醒版

## 本轮稳定性与 v1.3

- 已实现：提前续订账期选择、旧账期快照、跨 reload 写锁、付款请求编号持久化去重与冲突校验。
- 已实现：中文记账表单、真实付款日期、账单明细、取消/失败/重试反馈和手机操作布局。
- 已实现：默认关闭的到期提醒，本地 09:00 提前 7 天、3 天和当天发送站内通知，重载/重启去重、启动补发、卸载清理监听与任务。
- 已实现：HA 本地时区日历查询、有限金额校验、历史非法数值安全回退。
- 已补充：真实 Config/Options Flow、并发付款重试、提前多期付款、实际付款月份、日期与提醒回归测试。
- 待实际 HA 验收：升级资源缓存、真实站内通知展示、关机跨提醒阶段后的恢复、手机端交互。
- 2026-09-30 实机基础验收完成：本地设置备份、HACS v1.1.1 → v1.3.0、完整重启、两张资源路径更新、原订阅恢复、表单切换与取消。独立测试付款及提醒仍待验收，不改真实历史账期。
- 发布前自动验收已通过：55 项测试、Python/前端语法、JSON/YAML 和 diff；发布后继续核对 GitHub CI、版本标签及 Release。
- 后续：退款/更正与统一流水、数据导出、维修/保修和耗材低余量提醒；不在本轮引入大规模数据架构迁移。

## P0：阻断使用、数据损坏或严重兼容问题

当前没有已确认的 P0。若发现旧 Config Entry 无法迁移、实体唯一标识变化、配置被覆盖或服务导致持久化数据损坏，应暂停功能扩展并优先处理。

## P1：核心功能和数据正确性

- 已完成：修复续订服务省略 `cost` 时优先使用 `options.current_period_cost`，并增加回归测试。
- 已完成：续订服务拒绝今天及过去的明确到期日，防止写入立即过期的活动记录。
- 已完成：续订和耗材更换服务拒绝负数费用，避免静默转换为零。
- 已完成：修复上传目录创建使用 `async_add_executor_job` 关键字参数导致真实 HA setup 失败的问题。
- 在实际 HA 中验证旧 V1 条目迁移、旧卡片 `quick_action` 续订、显式费用/周期和续订后 `current_monthly_cost`。
- 已完成：增加真实 Config Entry fixture，覆盖实体注册、服务调用、reload/unload 生命周期；测试过程中修复真实 HA setup 的 executor 调用问题。
- 已完成：智能耗材检测持久化当天去重标记、跟踪并取消后台任务，并覆盖手动提醒/自动记账及状态边界。
- 已完成：兼容旧条目中 `consumables_list`/`accessories_list` 为空值或混入非对象记录的情况，避免传感器平台 setup 失败并让主体实体全部变为 `unavailable`。
- 已完成：兼容历史订阅条目误保存为 `idle` 的状态；服务类型现在按 `active/canceled` 解释，避免错误显示“闲置持有”并停止当前月度运行成本。
- 已完成：增加订阅附加支出记录，区分续订付款与升级差价/额外额度；基础预付费用按实际覆盖月数折算，追加费用按本月一次性增量计入，不改变到期日，并覆盖服务端与卡片入口。
- 已完成：增加参考月费、实际预付覆盖月数和付款明细；例如 140 元/月的 280 元预付明确表示覆盖 2 个月，付款覆盖与到期日不一致时显示可诊断提示。
- 剩余人工验证：在用户实际 HA 实例确认智能耗材通知展示、重启恢复和不同实体集成的状态变化。
- 明确分类编辑的保留/清理矩阵；若允许切换，必须设计 data/options migration，不可只改变展示分类。

## P2：稳定性、错误处理和架构

- 已完成：增加多 Config Entry 并行 setup/unload 测试，确认实体隔离、共享服务保持可用以及单条目卸载不影响其他条目。
- 已完成：覆盖多 Config Entry setup/unload/reload、共享服务与 HTTP view 的单次注册，以及最后一个 entry 卸载后的共享资源状态。
- 为损坏日期、非法金额、缺失子项目增加可诊断日志；保持兼容回退但避免静默掩盖数据问题。
- 已完成：通过真实 HA HTTP 客户端覆盖上传认证配置、PNG 签名、空文件、非法签名、超过 5 MB 的响应和磁盘写入异常，并验证随机文件名和实际落盘。
- 剩余：建立删除/替换记录后的旧图片清理策略。
- 评估附属项目分期到期语义、日历查询边界和所有 HA 时区/闰年边界。
- 如确实需要，再加入与目标 HA 版本匹配的类型检查；不要为了工具而重构业务模块。

## 验收要求

任何后续 P1/P2 修复都应：

1. 提供可复现条件和影响范围；
2. 覆盖成功、空值、不可用、重复调用、并发/reload 和异常路径；
3. 检查 entity ID、unique ID、Device Registry、旧 Config Entry data/options；
4. 执行可用测试和静态检查，并检查最终 diff/status；
5. 同步更新 `HANDOFF.md`、本计划和用户文档。
